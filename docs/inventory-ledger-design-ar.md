# تصميم دفتر حركات المخزون — Bein Store

## حدود المرحلة الحالية

هذه المرحلة تضيف قواعد مجال مستقلة واختبارات لها فقط. لا تتصل بقاعدة Supabase ولا تغيّر صفحة المخزون أو دورة الطلب الحالية، ولا تنشئ ترحيلًا قابلًا للتطبيق على الإنتاج.

## ما كشفته مراجعة النظام الحالي

- يوجد جدول `public.inventory` للرصيد الحالي وجدول `public.inventory_movements` للحركات.
- شاشة الإدارة تحفظ الرصيد عبر `admin_adjust_inventory`.
- إنشاء الطلب يخصم المخزون ويسجل حركة سالبة داخل معاملة قاعدة البيانات.
- إلغاء الطلب يعيد الكمية عبر `restore_order_inventory`، مع حماية حالية من الإرجاع المكرر تعتمد على مرجع الحركة وسببها.
- صلاحيات RLS الحالية تسمح للإدارة بإدارة سجل الحركات؛ لذلك لا يصح اعتبار السجل الحالي دفترًا غير قابل للتعديل بعد.

## قواعد دفتر الحركات المستهدف

1. كل حركة مرتبطة بمنتج ومصدر مستندي واضح، مثل استلام مشتريات أو تسليم بيع أو مرتجع أو تسوية.
2. لكل حدث مفتاح idempotency ثابت لا يتغير عند إعادة المحاولة.
3. يمنع تكرار المفتاح في قاعدة البيانات بقيد فريد؛ فحص JavaScript وحده لا يمنع سباق الطلبات.
4. تكون الحركات معتمدة بإشارات ثابتة: الاستلام والمرتجع الداخل موجب، والتسليم والمرتجع للمورد والخروج سالب.
5. لا تُعدّل الحركة المعتمدة ولا تُحذف؛ التصحيح يكون بحركة عكسية مرتبطة بالأصل.
6. تحديث الرصيد وكتابة الحركة يجب أن يحدثا ذريًا داخل PostgreSQL مع قفل صف الرصيد.
7. لا يُسمح برصيد سالب، ويجب أن تفشل العملية كلها دون أثر جزئي.
8. يجب أن تكون كل عملية بيع/إلغاء/مرتجع قابلة للتتبع إلى الطلب أو المستند المصدر، وألا تُسجل مرتين.

## قرار التوافق مع البيانات الحالية

لا ننشئ حركات افتتاحية تلقائيًا من الأرصدة الموجودة؛ ذلك يحتاج جردًا فعليًا وموافقة منفصلة. لا نحذف أو نعيد كتابة الحركات التاريخية. خطة الانتقال يجب أن تحفظ الأرصدة الحالية كما هي، وتبدأ من نقطة افتتاح معتمدة لكل منتج بعد مطابقة الجرد.

## ما لم يُنفذ بعد

- أضيفت Migration تجريبية تضيف تصنيف الحركة والمصدر ومفتاح idempotency، وتحمي السجل من UPDATE وDELETE وTRUNCATE.
- لم تُطبّق هذه Migration على مشروع Supabase المتصل أو الإنتاج؛ يجري اختبارها في PostgreSQL مؤقت داخل CI فقط.
- لم يتم بعد استبدال جميع مسارات الكتابة الحالية بواجهة تسجيل مركزية موحدة.
- لا يوجد ربط جديد مع شاشة المخزون أو checkout.
- لا يوجد تعديل للمنتجات أو الأرصدة أو الطلبات.
- تنفيذ قاعدة idempotency والقيود append-only يتطلب ترحيل SQL منفصلًا، واختبارات PostgreSQL معزولة، ومراجعة صلاحيات كاملة قبل أي تطبيق على المشروع الحي.

## طبقة حماية قاعدة البيانات المضافة للمراجعة

أضيف الملف `supabase/migrations/202611050002_inventory_ledger_append_only.sql` إلى هذا الفرع فقط. وهو:
- يضيف `movement_type`, `source_type`, `source_id`, `idempotency_key` ومرجع الحركة العكسية.
- يحافظ على السجلات القديمة ويمنح كل سجل قديم مفتاحًا فريدًا من معرّفه.
- يضيف قيد uniqueness على مفتاح idempotency.
- يصنف الحركات الناتجة عن checkout والإلغاء تلقائيًا لتوافق الدوال الحالية.
- يرفض تعديل أو حذف أو تفريغ سجل الحركات.

أضيف اختبار SQL منفصلًا للتحقق من التصنيف، ومنع تكرار المفتاح، ومنع UPDATE/DELETE/TRUNCATE. يشغّل CI الترحيل والاختبارات داخل حاوية PostgreSQL مؤقتة بعد اختبارات دورة الطلب.

هذه الطبقة لا تجعل كل عمليات تحديث الرصيد مركزية بعد؛ ما زال توحيد كل مسارات الكتابة وإضافة مفتاح طلب ثابت لتسويات الإدارة عملًا لاحقًا قبل اعتماد دفتر المخزون بالكامل.
